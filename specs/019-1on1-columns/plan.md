## Implementation Approach

### Step 1: Verify API Behavior

Before modifying the skill, verify the meetings API team filtering:

```bash
API_SH="<api.sh path>"
# Test 1: Check if team_id query param works
RESPONSE=$("$API_SH" GET "/meetings?team_id=TEAM_ID&per_page=5")

# Test 2: Inspect meeting objects for team fields
RESPONSE=$("$API_SH" GET "/meetings?per_page=5")
# Look for team_id, team, or group_id fields on meeting objects
```

Based on findings, choose the filtering approach:
- **If `team_id` query param works**: Use server-side filtering directly
- **If meetings have a team field**: Filter client-side by matching field
- **Fallback**: Filter by team member IDs (fetch team members, match person1/person2)

**Behavioral change**: The existing `--team` flag currently filters by participant membership (matching person1/person2 against team members client-side). This feature changes it to filter by team ID directly, which is simpler and more accurate. This is an improvement, not a regression.

### Step 2: Update List Flow in SKILL.md

Modify the "Flow: List One-on-Ones" section:

1. Add team ID resolution at the top (same pattern as other skills):
   - `--team {id}` flag → use that team ID
   - `default_team_id` in config → use that
   - Neither → show all meetings (no filter), add hint about `/rkit:setup`

2. When team ID is resolved, fetch team detail for the team name:
   ```bash
   TEAM=$("$API_SH" GET "/teams/TEAM_ID")
   ```

3. Fetch meetings with team filter:
   ```bash
   RESPONSE=$("$API_SH" GET "/meetings?team_id=TEAM_ID&per_page=100")
   ```

4. Client-side filter to `type: "one_on_one"` (always needed regardless of server filtering)

5. Update display header:
   - With team: `## One-on-Ones — {team_name} (ID: {team_id})`
   - Without team: `## One-on-Ones`

### Step 3: Update api-reference.md

If the `team_id` param on `GET /meetings` is confirmed working, update the master `api-reference.md` to document it, then run `/sync-plugin` to propagate.
